# GLM-5 昇腾性能实现总览

TorchTitanTurbo 只负责 Ascend 后端差异：Triton-Ascend 注册、torch_npu/CANN 算子、
HCCL/stream/graph 生命周期和必要兼容 patch。它不复制 TorchTitan 的 GLM 数学模型，
也不让 TorchTitan 反向依赖 Turbo。

## 已确认实现

### Triton-Ascend

```bash
--override.imports \
torchtitanturbo.models.glm5.ops.triton.npu_triton_dsa_indexer,torchtitanturbo.models.glm5.ops.triton.npu_triton_sparse_mla
```

它复用 TorchTitan `ops/triton.py` 的 Lightning Indexer 和 SparseMLA forward/backward，
只注册 NPU 组件类型。这样 GPU/NPU 的数学源统一，backend 差异留在 Turbo。

### Ascend native SparseMLA

```bash
--override.imports \
torchtitanturbo.models.glm5.ops.sparse_mla.npu_sparse_mla
```

该路径适配 `torch_npu.npu_sparse_flash_attention`，不替换 indexer。两个 override 都
默认关闭，普通 NPU precision/checkpoint/stability 行为不变。

## NPU 原型

- `compute/triton_topk_mask.py::triton_topk_additive_mask`：保留 INT32 index，
  用 Triton-Ascend fill+selected-write 替代 CANN INT64 scatter 的未注册候选；
- `communication/hccl_overlap_plan.py`：EP dispatch/GMM/combine 双缓冲依赖计划；
- `memory/graph_workspace_plan.py`：NPUGraph capture 前的静态、对齐 workspace layout。

Top-k mask 是可调用但未注册的 Triton candidate；另外两个只生成计划、没有 HCCL/CANN
调用。三者都不能作为跑通或性能结果。它们用于把 mask 语义、通信发起顺序、buffer
ownership、静态地址等设计先写清楚，具体伪接入见候选目录文档。

参考位置采用模块和符号定位：TorchTitan
`experiments/graph_trainer/ep_eager_chunk.py::maybe_apply_ep_overlap_eager_chunking`、
`distributed/linear.py::AllGatherLinear`；Megatron
`transformer/moe/token_dispatcher.py::MoEAlltoAllTokenDispatcher`；GLM 工程参考
`slime_plugins/models/glm5/ops/indexer.py::lighting_indexer` 和
`glm5.py` 的 `fused_select_topk` 局部函数。这里不导入上述外部符号。

## 分布式和图模式

- TP：SparseMLA 消费 TP-local head；
- EP：attention 在 dense-region，MoE 在 expert mesh，TP+EP 架构上可组合；
- CP：外层先形成 local-query/global-key，当前 correctness path 通信尚未优化；
- PP：受跨层 index sharing 的 stage 边界限制；
- graph：需要稳定 shape/address，避免 host sync，并验证 Triton-Ascend/CANN op 入图。

接口兼容不能代替实机验收。每条 NPU 路径都要依次完成 operator、single、目标拓扑、
eager 精度、graph 精度和 Ascend Profiler。

## 面试中的 NPU 性能判断

### 计算

看 AICore 利用率、kernel launch、HBM bytes 和 fallback/AICPU；Triton fusion 减少中间
读写，但需要关注寄存器、atomic、动态 shape 编译和 BF16 reduction。

### 通信

看 HCCL 是否位于 critical path，而不是只看通信总占比。优化需要把 dispatch/compute/
combine 分块并用 stream/event 重叠，同时保证各 rank 发起顺序一致，避免 deadlock。

### 内存和图

看 active/reserved、allocation event 和 graph replay。eager workspace pool 与 graph
static workspace 是不同设计：前者依赖 stream 顺序，后者依赖固定地址和固定 shape。

所有采集、A/B、正式精度和 HTML 报告均由 torchtitan-test 编排；候选原型在晋级前
不会成为其中的用户选项。
